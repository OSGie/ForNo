# خطة إثبات المفهوم العملي لمنصة موفوتر

## الهدف

سننفذ مشروع ويب واحدًا قابلًا للنشر يثبت رحلة بيع SaaS عربية متكاملة بصورة مبسطة وطبيعية. سيركز المشروع على صفحة هبوط احترافية موجهة للسوق المصري، وتخصيص التجربة لنوع العميل، واختيار الباقات، وتتبّع تسويقي قابل للربط لاحقًا، وCheckout واضح، ومحاكاة دفع خارجي ناجح، ونموذج عقد قابل للتنزيل، ولوحة تحكم مختصرة. الهدف هو عرض تجربة مستخدم واقعية وعالية الجودة، وليس بناء نظام إنتاجي معقد أو ربط دفع حي.

> **حدود الـPoC:** سيكون الدفع محاكاة آمنة عبر صفحة خارجية تجريبية، وسيكون إرسال نماذج الـExit-Intent والعقد محليًا داخل قاعدة المشروع. ستظهر في الكود والوثائق نقاط استبدال واضحة لربط PayTabs وCRM وتخزين الكائنات والبريد لاحقًا، لكن لن تُرسل أي بيانات أو تُنفذ أي معاملات حقيقية.

## مخرجات النسخة

| المساحة | ما سيتوفر في الـPoC |
|---|---|
| صفحة الهبوط | صفحة عربية RTL حديثة، مبنية من هوية موفوتر والأصول المرجعية، مع تصميم متجاوب، رسوم/صور أصلية احترافية، حركات خفيفة، وبنية تحويل واضحة. |
| التخصيص | اختيار «مكتب محاسبة» أو «شركة» في بوابة لطيفة غير معطلة، مع حفظ الاختيار وتبديل الرسائل والباقات والتوصيات. دعم `?p=firm` و`?p=company` ومعايير UTM المبسطة لتجاوز البوابة. |
| الباقات | بطاقات باقات وأسعار ومزايا، اختيار للخطة وللدورة ولإضافات اختيارية، وتحديث فوري لملخص الطلب. |
| التتبع | UID وجلسة وUTM وClick IDs في `localStorage` وcookie، طبقة `dataLayer`، ومجموعة أحداث مختصرة عالية القيمة. تحميل GTM وGA4 وMeta Pixel بمعرفات تجريبية قابلة للاستبدال من ملف إعدادات. |
| Checkout | نموذج عربي منظم للتحقق من بيانات العميل، استعراض سعر وVAT 14%، وحفظ طلب Demo خادمي/محلي. |
| الدفع | صفحة محاكاة لـPayment Link خارجي ثم عودة نجاح؛ لن يحدد المتصفح الحالة وحده بل يستدعي إجراء خادمي محلي يحاكي اعتماد webhook. |
| العقد | يظهر بعد نجاح الطلب فقط، ويعرض نموذج بيانات العقد، ثم يولد نسخة HTML قابلة للطباعة/التنزيل باستخدام النص الحرفي من `FullContract.html` وبيانات دمج واضحة. |
| لوحة التحكم | لوحة مبسطة محمية تعرض الزوار والجلسات والمصادر واختيار الشخصية ووصول الأسعار والـCheckout والطلبات الناجحة، مع جدول أحداث حديثة. |

## ما لن يدخل في هذه النسخة

| غير مشمول | سبب الاستبعاد |
|---|---|
| PayTabs أو بطاقات أو Refunds حقيقية | النسخة Proof of Concept ولا تحتاج أسرار دفع أو التزامات مالية. |
| معالجة PDF على الخادم أو S3 أو روابط موقعة | سيكفي تنزيل/طباعة HTML محليًا، مع وضع واجهة خدمة قابلة للاستبدال لاحقًا. |
| 52 حدثًا وتحليلات Attribution كاملة أو outbox | ستُنفذ قائمة أحداث مركزة تثبت أن النموذج صحيح ويمكن توسيعه دون إعادة بناء. |
| CRM أو Google Sheets أو البريد الحقيقي | ستسجل البيانات محليًا فقط مع طبقة Adapter واضحة للنقاط المستقبلية. |
| لوحة إدارية متعددة الأدوار وإجراءات تشغيل معقدة | ستبقى لوحة قراءة مبسطة للمستخدم المالك في القالب الحالي. |
| جدولة ومهام دورية ومصالحات دفع | لا حاجة لها بدون ربط دفع خارجي حي. |

## التتبع في الـPoC

يُبنى ملف ES5 مستقل باسم `mof-track.poc.js` لإنشاء `visitor_id` و`session_id`، وحفظ أول مصدر وآخر مصدر، والتقاط UTM و`fbclid` و`gclid` عند وجودهما. وسيدفع الأحداث إلى `window.dataLayer` وإلى endpoint داخلي عبر `XMLHttpRequest`. ستوضع معرفات GTM وGA4 وMeta Pixel في ملف إعدادات مثالي بقيم تجريبية، ولا تُستخدم أي مفاتيح أو بيانات تعريف شخصية حقيقية في المنصات الخارجية.

| الحدث | موضع الإطلاق |
|---|---|
| `session_started` و`page_view` | تهيئة الصفحة. |
| `persona_gate_viewed` و`persona_selected` و`persona_gate_skipped` | بوابة الشخصية. |
| `landing_viewed` و`section_viewed` و`cta_clicked` | التفاعل الرئيسي مع الهبوط. |
| `pricing_viewed` و`plan_selected` و`checkout_started` | مرحلة القرار الشرائي. |
| `lead_submitted` | نموذج الـExit-Intent أو نموذج طلب العرض، محلي فقط. |
| `order_created` و`payment_simulated_success` و`purchase_completed` | Checkout وصفحة الدفع التجريبية والاعتماد الخادمي المحلي. |
| `contract_generated` و`contract_downloaded` | إنشاء العقد وتنزيله. |

## خطوات التنفيذ

| الترتيب | الخطوة | الناتج القابل للتحقق |
|---:|---|---|
| 1 | إعادة ضبط الهيكل على نطاق الـPoC، وحذف الاعتماد على التعقيد غير المطلوب، وتثبيت تكوين المحتوى والهوية. | تطبيق RTL مع هوية موفوتر، ملفات محتوى عربية، وفاحص عبارات الامتثال. |
| 2 | بناء مخطط بيانات صغير للزوار والجلسات والأحداث والجهات والطلبات والعقود، مع بيانات الباقات المؤكدة من المرفقات. | جداول وترحيل وبيانات Seed وخدمة تسعير بالأقراش وضريبة 14%. |
| 3 | إنشاء طبقة التتبع ES5 وواجهة استقبال داخلية ودمج `dataLayer` وإعدادات GTM/GA4/Meta التجريبية. | أحداث تجريبية مرئية في اللوحة وتُحفظ في قاعدة البيانات. |
| 4 | تصميم وتنفيذ صفحة الهبوط: hero قوي، إثبات بصري، اختيار الشخصية، مزايا، لقطات المنتج، باقات، FAQ، CTA، Exit-Intent وشريط جوال. | تجربة تحويل متجاوبة وجذابة على الجوال وسطح المكتب. |
| 5 | تنفيذ Checkout وخطوات التحقق وحساب السعر وملخص الطلب والتحويل إلى صفحة دفع تجريبية. | أمر تجريبي متماسك من اختيار الباقة حتى شاشة الدفع الخارجية. |
| 6 | تنفيذ callback تجريبي خادمي وحالة النجاح ثم نموذج العقد والنسخة القابلة للتنزيل. | لا يظهر العقد إلا بعد اعتماد نجاح محلي على الخادم. |
| 7 | إنشاء لوحة تحكم قراءة مبسطة، اختبار المسار كاملًا، وتحسين التفاصيل البصرية وRTL وإمكانية الوصول. | لوحة مؤشرات حقيقية من بيانات الـPoC واختبارات مرور رئيسية. |

## التزامات الامتثال

سيبقى النص العام عربيًا فقط، وستستخدم عبارة **«متوافق مع متطلبات مصلحة الضرائب المصرية»** دون أي ادعاء اعتماد أو ترخيص. ولن يطلب المشروع بيانات دخول بوابة الضرائب أو توكيلًا. كما ستظل أرقام الادعاءات من ملف `claims.json` مع `isPlaceholder`، وسيبقى نص العقد من `FullContract.html` حرفيًا مع حقول الدمج المحيطة فقط.

## معايير القبول

| المجال | معيار القبول |
|---|---|
| تجربة المستخدم | صفحة هبوط متجاوبة ومميزة بصريًا، واضحة على الجوال، ونصوصها وأرقامها صحيحة الاتجاه. |
| الرحلة | يستطيع المستخدم اختيار شخصية وباقة، استكمال Checkout، عبور دفع تجريبي، إدخال بيانات العقد، وتنزيل نسخة منه. |
| التتبع | تظهر UTM/UID والأحداث الرئيسية في `dataLayer` وقاعدة البيانات ولوحة الـPoC. |
| الأمان المنطقي | لا يتحول طلب إلى «ناجح» من متغير واجهة؛ يأتي الاعتماد من إجراء خادمي تجريبي واحد. |
| القابلية للتوسعة | ملفات الإعدادات والـAdapters توضح مواضع ربط GTM/GA4/Meta وPayTabs وCRM والتخزين الحي لاحقًا. |
| الجودة | يمر TypeScript والاختبارات الأساسية، ولا توجد عبارات امتثال محظورة أو نص قانوني معاد صياغته. |
